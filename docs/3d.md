# Botões "2D"/"3D" do CADe_SIMU — o que fazem (RE do binário, 15/10/2026)

Resumo: **não há motor 3D** (nem OpenGL, nem DirectX, nem arquivos de modelo). "3D" é uma
**imagem bitmap embutida no EXE** (fotos/renders de componentes) desenhada no lugar do
símbolo, escolhida pelo campo **n16** da própria entidade. Um gerador de `.cad` não precisa
preencher nada para o 3D funcionar: basta gravar `n16 = 0` (Símbolo). O botão 3D reescreve
`n16` em memória para as classes que têm imagem.

## Evidência

| item | onde | confiança |
|---|---|---|
| Barra "Visualiza símbolo / componente 2D / componente 3D / 2D-3D anterior" = comandos 33358/33361, 33359, 33360, 33367 | STRINGTABLE (tooltips `"Visualiza componente 3D\n…"`) + message map `ON_COMMAND` em `.rdata` 0xb4adb8..0xb4ade8 | alta |
| Handler 3D = `FUN_004a2340` (2D = `FUN_004a1080`, Símbolo = `FUN_0049fe30`) | thunks 0x401659 / 0x402f18 / 0x4023dd | alta |
| O handler grava `DAT_00b80800 = 2` (1 = 2D, 0 = símbolo) — global **só escrita**, nunca lida | xrefs de 0xb80800 (3 writes) | alta |
| Para cada entidade das classes abaixo: salva `n16` original em `+0x8c31c` (se ainda −1) e troca `n16 (+0x177e4)` pelo índice "Imagen 3D" da variante (ex.: motor 1000 → 4; 7016/7019/6015.. pares 0/1→2, 3/4→5, 6/7→8; 8100/8101 → 3 ou 6) | `FUN_004a2340` decompilado | alta |
| "Visualiza 2D 3D anterior" restaura `n16` a partir de `+0x8c31c` (buffer só em memória, não serializado) | idem | média |
| Desenho: a rotina da classe testa `n16` (ex.: motor `CMP [ent+0x177e4],4` e `n17`/simulação desligada) e chama `FUN_008c04e0(nome)` | `FUN_004a8d80` @0x4aa7b5 | alta |
| `FUN_008c04e0`: tabela nome→ID (`"MOTOR_3D"`, `"LED_VERDE_3D_ON"`, `"S7_1200_3D"`, `"ARDUINO_UNO_3D"`, …) → `CBitmap::LoadBitmap(id)` (Ordinal_3421) → `StretchBlt` (Ordinal_4978) com tamanho fixo por imagem | decompilado (140 nomes nessa função; outras famílias, ex. `TERMICO_3D_ON`, `DISYUNTOR_3D_OFF`, `RELE_3D_ON`, em rotinas irmãs) | alta |
| Recursos: **274 RT_BITMAP** (~31,8 MB) no `.rsrc`; nenhuma DLL/string OpenGL, Direct3D, DirectDraw, GDI+ | varredura do PE | alta |

## Classes com representação 2D/3D (as que o botão altera)

1000, 1001 (motores), 1076, 4011 (régua de bornes: "Imagen 2D blanco/gris/azul/tierra"),
6015..6020 (disjuntor, relé térmico, interruptor automático/diferencial, interruptor,
seccionador "modulares"), 7016..7021 (relé, relé temporizado de zócalo, contator 7018 e blocos
de contatos auxiliares/ON-delay/OFF-delay), 8100..8103 (pulsador, piloto, botoeira, LED),
10202..10204, 10209..10215, 10220 (LOGO, S7-1200, S7-1500, ET-200, Arduino UNO).

As opções de cada classe estão em `docs/classes-papeis.json` → `representacao.opcoes_dialogo`
(ordem = valor de `n16`). Exemplo motor 1000: `0 Símbolo, 1 Imagen 2D, 2 Imagen 2D-Y,
3 Imagen 2D-D, 4 Imagen 3D`. As demais classes (contatos 7000.., bobinas, botões 8000..) **não
têm 3D**: o botão não as altera e elas continuam como símbolo.

## Dependências no `.cad`

- Só **n16** (índice 16 dos ints da entidade). No acervo (110 arquivos): motor 1000 `n16=0` em
  70 e `=4` (3D) em 1; 2001/9008/4011 sempre 0; 8100 com 3 e 6; 6017 com 23.
- `n18` não participa do 3D (é variante/estado). Não há arquivo externo nem caminho de imagem.
- Pinos × representação: **hipótese não verificada** — as rotinas de desenho têm ramos por
  `n16` e o ponto-pino sai do `NUME` executado no ramo; classes com imagem (ex. 7017, cujos pinos
  em `pinos-binario.json` vão a y=90) podem ter pinos diferentes no 2D/3D. Por isso **o gerador
  deve manter n16 = 0** para que os pinos medidos valham.

## Recomendação para o gerador

Gravar `n16 = 0` em todas as entidades elétricas (já é o que fazemos). Se quiser abrir em 3D,
o usuário clica no botão; gerar com `n16` = índice 3D só é seguro para as classes acima, e os
pinos podem mudar de lugar (não medido).
